    2026-10-23 · Batch 2: multi-enemy and target selection¶

    Duration: afternoon Commits: this very commit.

    Objective¶

    Make the biggest jump in depth on the roadmap: several enemies per combat and being able to choose who you attack. Use the session to open Unity, really try it and set up the skills system for the coming sessions.

    What was done¶

    • Multi-enemy. CombatSession no longer has a single enemy: it holds a list of EnemyInstance, each with its own HP, block, Vulnerable and intent cursor. The combat ends when they all fall.
    • Target selection. CombatSession.Target with SelectTarget; when the target dies, the next living one is auto-selected. Attack cards hit the target; Cleave becomes DamageAll and hits every enemy.
    • Combat screen. Row of clickable enemies with a health bar, block and intent per enemy; the target gets a gold outline, the dead ones stay dimmed with DEFEATED; floating numbers and flashes go to the panel of the enemy hit.
    • Encounters. RandomEncounter returns 1 normal enemy (55%) or a pack of two weaker variants (JawWormPack 22 HP, CultistPack 24 HP), repeated or mixed; duplicated names get an A/B suffix.
    • Test tools. KILL TARGET button in the F1 panel and the current target in the status line. New tools/compile-check.ps1 to compile without opening Unity.
    • Skills. Created .opencode/skills/ (unity-ugui-code, deckbuilder-balance, unity-verify, gameplay-architecture) and prepared status-effects-pipeline for the next session. The start/end session workflow in AGENTS.md now includes loading them at the start and preparing them at the end.

    !!! note "Extension from 2026-10-27" These five are the project skills. Later, nine external skills copied from the skills.sh catalogue were added: general knowledge (uGUI, Input System, card zones, roguelikes) is no longer written from scratch. See External skills.

    Decisions¶

    • EnemyInstance separate from EnemyData: the definition (ScriptableObject) is not touched; combat state lives in one object per enemy. That is what will allow Strength/Weak per enemy without dirtying the catalogue.
    • Packs with weak variants instead of scaling HP: two enemies of 44-50 HP with 11 damage would have been unplayable with 3 energy. Explicit variants = readable, easy to tune numbers.
    • DamageDealt(int, EnemyInstance) with null = player: one event for all floating numbers, without duplicating feedback code.
    • Target by click (Outline + colour), not by keys: less code and more discoverable. Auto-selection of the next living enemy so the hand is not blocked.
    • DamageAll as its own effect instead of a flag on the card: the effects switch is already the extension point and the card says so in its text.
    • compile-check.ps1 in the repo: compiling with Roslyn against the DLLs in Library/ takes 2 s and lets you verify without opening the Editor. It complements, does not replace, the Play mode test.
    • Skills in the repo: expensive knowledge (anchors, numbers, MCP recipes) should not be re-derived every session. They are prepared at the end, looking at the next 1-2 roadmap items.
