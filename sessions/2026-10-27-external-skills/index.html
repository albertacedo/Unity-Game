    2026-10-27 · External skills from skills.sh¶

    Duration: afternoon Commits: 3183de6 — skills: nine skills vendored from the skills.sh catalogue

    Objective¶

    Stop writing skills by hand. The engineering and design knowledge we use every session (uGUI, MonoBehaviour lifecycle, Input System, card zones, run economy) is not ours: it exists in public agent skills catalogues. Today's job is to bring it in from outside, versioned in the repo, instead of reinventing it.

    Method: how they are found and installed¶

    1. The API is closed. https://skills.sh/api/v1/skills/search?q=... returns 401 authentication_required: it wants a Vercel OIDC token. Not an option for a local project.
    2. The web search does work. The https://www.skills.sh/search?q=<term> pages are server-rendered: opening them in a browser shows the whole list (skill, repo, installs). The pages https://www.skills.sh/<owner>/<repo>/<slug> carry the install command and the security audits.
    3. Vendored installation. Instead of npx skills add (which writes to the agent's global folder and does not stay in the repo), the upstream is downloaded and copied to .opencode/skills/<slug>/, with an Upstream source footer.

    The full loop, to repeat it whenever a skill needs updating or adding:

    # 1. Find the real path inside the repo (routes vary: skills/, skills/unity/, SKILL.md at the root)
Invoke-RestMethod "https://api.github.com/repos/<owner>/<repo>/git/trees/main?recursive=1" |
  Select-Object -ExpandProperty tree | Where-Object { $_.path -like "*SKILL.md" }

# 2. Download the SKILL.md and the files it references (references/, scripts/)
Invoke-WebRequest "https://raw.githubusercontent.com/<owner>/<repo>/main/<path>/SKILL.md" `
  -OutFile ".opencode/skills/<slug>/SKILL.md" -UseBasicParsing

    Decisions¶

    • Vendor, do not install globally. The repo is what has to know what it works with; a global install does not travel between machines and does not stay in the history.
    • The body belongs to upstream. Only the provenance footer is added (repo, path, date, audits) and, if needed, the normalisation of a broken description. Divergences with the project are documented in the project skill, not by editing the external one.
    • When they clash, the project one wins. unity-ugui-code knows the UI is built from code and at 1600×900; ui-ugui assumes prefabs and the Editor. The external ones are general doctrine.
    • Searching outside is step 1. The end-of-session routine in AGENTS.md now says, in this order: search skills.sh for the general knowledge behind the next 1-2 roadmap items; write a project skill only for what upstream cannot know (this repo's numbers, classes, pitfalls and verification); and update the existing ones if the session changed how they work.
