# 2026-10-22 · Batch 1: observe and test

**Commit:** `4a352c0` — *feat: playtest tools - dev panel, deck viewer, combat feedback*

## Objective

Make the prototype **observable and testable** before adding content: tools to jump to any
state, a way to see the deck and visual feedback in combat.

## What was done

### Development panel (`F1`)

Overlay in the bottom-left corner with the current state (seed, HP, deck size, gold,
energy) and these buttons:

| Button | Effect |
|---|---|
| HEAL TO FULL | Heals to full (map and combat) |
| ADD RANDOM CARD | Adds a card from the reward pool |
| WIN COMBAT | Closes the combat as a victory |
| +1 ENERGY | Extra energy for the turn |
| SKIP ROOM | Skips the current room (or picks a random one on the map) |
| RESTART (SAME SEED) | Restarts with the same map |
| RESTART (NEW SEED) | New run |

### Deck view

Overlay on top of any screen (`VIEW DECK` on the map and in combat):

- grid with *scroll*, sorted by type and name
- click a card → it doubles in size with type and cost
- `ESC` closes it (first the detail, then the overlay)
- it destroys itself when the screen changes

### Combat feedback

- `CombatSession` now exposes `DamageDealt(int amount, bool hitPlayer)`
- **floating damage numbers** that rise and fade (gold on the enemy, red on you)
- **flash** on the matching panel (white on the enemy, red on the player)

### Supporting refactor

- `GameManager` registers the active screen (`ScreenKind`) and exposes `Run`, `Combat`,
  `InCombat` and the `Debug*` methods.
- `CombatSession` gains `NotifyChanged()`, `AddEnergy()` and `ForceVictory()`.

## Decisions

- The dev panel **does not** modify the game flow: it only calls the same methods a click
  would.
- The deck view is an **overlay**, not a screen: that way it works the same on the map, in
  combat and in rewards.
- The feedback was done with **coroutines** instead of DOTween: zero new dependencies.
- `ADD RANDOM CARD` in combat only touches the run deck, not the piles of the current
  combat.
